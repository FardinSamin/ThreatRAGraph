# M4 — Cold-Start B0 Report-Only Baseline

**Status:** Deterministic, testable **B0 research reference implementation**. Only synthetic sources/cases reviewed in tests; no historical pilot corpus, validated original prototype, or empirical research results.  
**Tracking:** [Issue #19](https://github.com/FardinSamin/ThreatRAGraph/issues/19)  
**Traceability:** [SRS](SRS.md) RC-04–06, FR-19, FR-23–24, FR-28, DR-09; [SDD](SDD.md) §4.2, §5 and §9.

## Research purpose

ThreatRAGraph's paired experiment compares:

- **B0**: a cold-start profile from **the case's first one or two public reports only**.
- **G1 (future milestone M5)**: those same early reports plus historically eligible graph-background knowledge, retrieving structurally similar historical cases.

B0 is the **report-only comparator**, not a prediction model, pretraining prior or similarity engine. A source's report claim is not necessarily true in the external world. The baseline deliberately makes **no novel inferred relationships**.

### Input trust boundary

The **standalone B0 process accepts precisely two JSON artifacts**:

1. A validated M3 **B0-only** \`historical_source_input\` view with one/two unique early source-version IDs, exact UTC cutoff and frozen SHA-256 metadata.
2. The corresponding M2 **B0-only** \`historical_sourced_graph\` projection, with citation-aligned and human-review-status-tagged sourced edges.

It **does not accept** a full case manifest, G1 graph, entire source registry, unrestricted SQLite file, reference labels, background corpus, internet connection, or any LLM. Input artifacts must originate from the existing approved source-integrity, review and history-gated preparation pipeline. **The B0 consumer revalidates identity and time constraints but cannot independently prove that externally provided JSON was generated by a trustworthy process.**

The CLI checks:

- \`method=B0_sparse_report_only\` and correct artifact contracts;
- source view SHA-256 fingerprint matches the graph's \`source_view_sha256\`;
- exact case ID and cutoff match;
- 1–2 distinct, pre-cutoff source versions all tagged \`role=early\`;
- **every graph edge** has a source-version ID in that early allowlist;
- all graph nodes equal endpoints of exactly those sourced edges (no injected neighbors);
- every claim is source-asserted with a unique content-derived claim ID, typed relationship and aligned citation;
- source review status belongs to the explicit reviewer-decision vocabulary;
- strict mode refuses missing, uncertain or unsupported semantic reviews.

Extra fields such as \`later_reference_source_version_ids\`, \`outcome_labels\`, reference text, or unrestricted background source metadata are rejected **at the input-contract boundary** rather than passed through as profile context.

## Profile algorithm: \`b0-assertions-v1\`

The algorithm evaluates exactly the reviewed edges in the B0-only projection. It:

1. Selects only relations whose **subject or object matches the exact canonical target entity ID** in the validated B0 source view. It does not guess that aliases and lookalike names are identical.
2. Rejects unsupported review states from strict research runs. Development mode counts them but never emits those claims as observed facts.
3. Preserves only **positive assertions**; uncertain and negative assertions never become positive predictions. When a positive and a negative claim share the same subject/predicate/object triple, it omits that triple as conflicted.
4. Groups duplicate assertions of the same triple into one profile fact while preserving every independent **claim ID, source version and evidence SHA-256**. Duplicate mentions from one report cannot inflate source counts.
5. Sorts grouped facts, source IDs and claims to produce a deterministic profile ID and byte-stable JSON independent of incoming graph edge order.
6. Emits **no inferred predictions**. No graph-neighbor similarity, probabilistic confidence, pretrained language-model enrichment, related-CVE crosswalks or ontology-based inverse facts are used.
7. Explicitly **abstains** when no uncontradicted, positive, reviewer-supported target fact remains; distinguishes contradictory evidence and insufficient review.

### Output contract

The versioned JSON record carries:

| Field | Meaning |
|---|---|
| \`profile_id\` | Content-derived hash of profile fields (excluding ID), useful for reproducibility |
| \`schema_version\`, \`profile_kind\`, \`method_version\` | Exact \`1.0\` B0 profile and \`b0-assertions-v1\` contract |
| \`case_id\`, \`cutoff_at\`, \`target_entity_id\` | Case and historical cutoff identity |
| \`source_view_sha256\`, \`early_source_version_ids\` | Frozen permitted early input identity |
| \`facts[]\` | **Source-asserted** target triples with claim/source/evidence provenance, review support and \`score=null\`, \`confidence=null\` |
| \`predictions[]\` | **Always empty for this v1 baseline**; no extrapolation |
| \`abstention\` | Explicit boolean and reason when no valid positive target assertion remains |
| \`diagnostics\` | Counts of unreviewed/uncertain/non-target/negative/conflicted claims |
| \`research_ready\` | False for synthetic \`--development-only\` runs; strict mode still depends on upstream corpus validation |

**\`score=null\` is deliberate.** Two agreeing reports and five copy-pasted claims do not automatically translate to a probability or calibrated confidence. G1's later similarity scores must also disclose that they are uncalibrated until benchmark evidence supports calibration.

B0 facts mean *“an approved initial report asserted this relationship, and the citation was aligned/reviewed.”* They **do not** certify that an observed security event actually occurred.

## Standalone CLI

~~~powershell
python -m scripts.profile_b0 --b0-view "C:\research\b0-view.json" --b0-graph "C:\research\b0-graph.json"
~~~

For **synthetic fixtures only**, including those with unreviewed claims:

~~~powershell
python -m scripts.profile_b0 --b0-view "C:\research\b0-view.json" --b0-graph "C:\research\b0-graph.json" --development-only
~~~

The CLI prints deterministic JSON to stdout, makes no network or AWS calls and requires only the Python standard library **to execute the baseline itself**. The complete repository tests require the pinned PDF/Falco normalization dependencies.

**Preparing the two inputs is a separate trusted upstream stage**, currently represented by the M3 \`case_views(...)[\"B0\"]\` source view and M2 \`EvidenceGraph.project(B0_VIEW)\` after approved archival evidence/semantic review; these artifacts are not yet generated for real CTI data. The previously implemented case graph CLI returns both B0 and G1 as an internal researcher result; **do not feed its entire response to the baseline**. Export the B0 view and B0 graph into separate files, and invoke this isolated CLI on those files only. End-to-end synthetic fixtures illustrate the interface.

Example recorded, synthetic \`facts[]\` structure:

~~~json
{
  "subject_id": "malware:synthetic",
  "predicate": "USES",
  "object_id": "attack-technique:T1059",
  "status": "asserted_in_early_reports",
  "source_version_ids": ["srcver:synthetic-early-v1"],
  "supporting_claim_ids": ["claim:<full-valid-claim-digest>"],
  "evidence_sha256s": ["<real-digest-required>"],
  "confidence": null,
  "score": null,
  "score_kind": "not_estimated"
}
~~~

This is **illustrative**, not a real source fact or a valid complete input artifact. The baseline never invents support IDs.

## Tests and remaining limitations

~~~powershell
python -m pip install -r requirements-normalization.txt
python -m unittest discover -s tests -v
python -m scripts.profile_b0 --help
~~~

The synthetic tests cover one/two early reports, claims with multi-source support, stable output despite reordered edges, contradicting positives/negatives, negation, uncertainty, exact target matching versus similar aliases, disallowed graph-neighbor traversal, injected G1 graph/source roles, invalid future availability timestamps, held-out claims and labels, wrong snapshot digests, duplicate claims, unaligned citations, unreviewed strict refusals, zero-data abstention, standalone CLI and the existing historical graph+review pipeline.

**Research limitations that remain:**
- B0 doesn't identify unreported behavior; it describes **only early supported source assertions**. Comparability with G1 must use a preregistered fact/ontology and scoring protocol rather than give G1 credit for outputting more speculation.
- Any pre-extracted claim using future-informed language-model weights/aliases can contaminate B0 **before** this algorithm sees it. Those must be controlled at original extractor/case reconstruction.
- Strict \`research_ready\` means the supplied B0 contract and review requirements passed; this lightweight profiler cannot reverify original immutable source archives or publisher chronology. Upstream M1/M2 checks and human review are mandatory.
- The current repository has **14 unapproved candidate URLs and no validated cases**; no true B0 baseline experiment has been run.
- Original local prototype import (#1), exact source chronology (#3), reviewed real claims and paired B0/G1 results remain pending.

**M5** is the next proposed implementation: a separate, time-valid graph-structural similarity candidate engine with attributable feature contributions, inferred-edge isolation and abstention. Do not merge G1 features into this B0 code.
